## 1. 背景

架空の会社「サンプル商事」（社員約80名・5部署）では、経費の立替精算と備品購入の申請を、紙の申請書とメールで回している。

## 2. これまでの課題

| 課題 | 内容 |
|------|------|
| 承認の滞留 | 申請書が承認者の机やメールの受信箱に埋もれ、承認まで平均1週間ほどかかる。誰の所で止まっているかが分からない。 |
| 承認者の判断ミス | 金額によって承認者が変わる社内規程を申請者が覚えておらず、違う上長に回して差し戻しになる。 |
| なりすまし・二重処理 | メールの「承認します」という返信だけでは本人の承認か確かめられない。同じ申請を二度処理してしまうことがある。 |
| 記録が残らない | 誰がいつ承認したかが紙とメールに分散し、監査のときに集めるのに時間がかかる。 |

## 3. 目的

- 申請から承認・通知までを自動で回し、承認の滞留を減らす。
- 承認者は社内規程（部署・金額）に沿って自動で決まるようにする。
- 承認操作は本人だけが、1回だけ行えるようにする。
- すべての操作を記録し、後から追えるようにする。

## 4. 用語

| 用語 | 意味 |
|------|------|
| 申請 | Google フォームから送られた経費・備品購入の依頼1件 |
| 承認経路 | 申請1件について、誰がどの順番で承認するかの並び |
| 段階 | 承認経路の中の順番（1段目・2段目）。各段階に1人の承認者が対応する |
| 承認リンク | 承認者に送るメール内のリンク。開くと承認画面が表示される |
| トークン | 承認リンクに含まれる、改ざんを見破るための署名付きの文字列 |
| 監査ログ | 誰が・いつ・何をしたかを追記していく記録用のシート |

## 5. 機能要件

| ID | 要件 | 優先度 |
|----|------|--------|
| REQ-001 | Google フォームから送信された申請を受け付け、申請一覧シートに記録する。 | 必須 |
| REQ-002 | 部署と金額に応じて承認者を自動で決める。規則は承認ルールシートで変更できる。 | 必須 |
| REQ-003 | 金額がしきい値（設定シートで指定）以上の申請は、部署の承認者に加えて最終承認者の2段階で承認する。 | 必須 |
| REQ-004 | 承認者に、承認・却下を行う画面へのリンクをメールで送る。 | 必須 |
| REQ-005 | 承認・却下の結果を申請一覧に反映し、申請者にメールで知らせる。2段階の場合は次の承認者へ回す。 | 必須 |
| REQ-006 | 一定時間処理されていない申請の承認者に督促メールを送る。督促回数が上限に達したら管理者に知らせる。 | 必須 |
| REQ-007 | 申請の受付・承認・却下・督促・失敗した操作を監査ログに記録する。 | 必須 |
| REQ-008 | 申請者本人が自分の申請を承認する経路を作らない（代わりの承認者に回す）。 | 必須 |

## 6. 非機能要件

| ID | 区分 | 要件 |
|----|------|------|
| REQ-101 | なりすまし防止 | 承認リンクは改ざんを見破れる署名付きとし、さらに画面を開いた人が割り当てられた承認者本人かを確かめてから状態を変える。 |
| REQ-102 | 二重承認防止 | 承認リンクは1回しか使えない。承認済み・却下済みの申請は、同じリンクでも別のリンクでも再度処理できない。 |
| REQ-103 | 有効期限 | 承認リンクには有効期限（初期値72時間）を設ける。期限切れのリンクでは操作できない。 |
| REQ-104 | 監査ログ | 監査ログは追記のみとし、プログラムから既存行の書き換え・削除をしない。シートは管理者以外が編集できないよう保護する。 |
| REQ-105 | 権限 | Google への権限（OAuth スコープ）は必要最小限とし、外部から呼べる関数を限定する。 |
| REQ-106 | 秘密情報 | 署名に使う鍵はプログラムに書かず、スクリプトのプロパティに保存する。 |
| REQ-107 | 同時操作 | 同じ申請に同時に操作が来ても、状態が壊れない（排他制御を行う）。 |
| REQ-108 | 検証可能性 | 承認経路の決定・トークン・状態遷移・督促対象の選定は Google のサービスから切り離し、手元の Node.js で自動テストできる構成にする。説明用の架空データを手元で作れるようにする。 |
| REQ-109 | 操作性 | 承認画面はスマートフォンでも操作できる。押し間違いを防ぐため、承認・却下は確定前に確認を表示し、送信中は二重に押せないようにする。 |

## 7. 対象外

- 申請の取り下げ・修正（必要なら再申請とする）
- 承認者の不在時の代理設定（督促の上限に達した後に管理者に知らせる運用で代替する）
- 会計システム・ワークフロー製品との連携
- 添付ファイル（領収書画像）の保管と確認
- 社外（Google Workspace のドメイン外）の利用者からの承認

## 8. 前提・制約

- 会社は Google Workspace を利用しており、申請者・承認者は同じドメインのアカウントを持つ。
- 本リポジトリの例に出てくる会社名・氏名・メールアドレス（example.com）はすべて架空である。
- 実際の Google 環境では、主な流れ（受付・承認・却下・督促）だけを確認した。2段階の承認などは未確認である。詳細は [05_テスト仕様書](05_テスト仕様書.md) の3章を参照。
