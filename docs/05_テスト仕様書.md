## 1. 方針

| 区分 | 方法 | 実施 |
|------|------|------|
| 純粋ロジック | Node.js の標準テスト機能（`node:test`）で関数を直接呼ぶ | 実施（下表） |
| GAS のサービスを使う処理 | ビルド済みの `dist/*.js`（clasp で送るものと同じファイル）を Node.js の `vm` で1つのグローバル空間に読み込み、SpreadsheetApp・MailApp・PropertiesService・LockService・Session・ScriptApp・HtmlService・Utilities を代替部品（モック）に差し替えて通しで動かす | 実施（下表） |
| 承認画面の画面側スクリプト | テンプレートを HtmlService の代替部品で展開し、最小限の DOM の代替部品の上で画面側のスクリプトを実行する | 実施（下表） |
| Google 環境での動作 | 実際のスプレッドシート・フォーム・ウェブアプリ・トリガー・メール送信 | 主な流れを実施（3章）。2段階の承認などは未実施 |

代替部品は本プロジェクトが使う部分だけを再現している。HMAC は Node.js の `crypto` で計算し、GAS と同じく符号付きバイト配列と web-safe base64 の形で返す。HtmlService の代替部品は印字スクリプトレット `<?= ?>` の HTML エスケープだけを再現しており、GAS の文脈に応じたエスケープ全体を再現するものではない。

## 3. Google 環境での確認

2026-11-16 に、実際の Google 環境で主な流れを確認した。確認の結果（確認できた項目・できなかった項目）は 3.2 に、確認の中で見つかった点は 3.3 に記載する。

### 3.1 確認の環境と方法

| 項目 | 内容 |
|------|------|
| アカウント | Google Workspace のアカウント1つ（承認者・管理者・スクリプトの所有者を兼ねる）と、組織外の個人アカウント1つ（申請者） |
| 配置したもの | `npm run build` の結果を `clasp push` で送り、`clasp clone` で取り戻して `dist/` の14ファイルと一致することを確かめた。`appsscript.json` は本リポジトリのまま（スコープ4つ、ウェブアプリは「自分として実行」「組織内のユーザーのみ」） |
| 設定の変更 | 申請者を組織外のアカウントにするため、確認用のフォームだけ「組織内のユーザーに限定」を外した。督促の確認のため、設定シートの督促開始時間を 1 時間にした |
| データ | 架空の申請3件（REQ-20261116-0001〜0003）。確認後に、スプレッドシート・フォーム・スクリプトを削除した（ゴミ箱へ移動） |

### 3.2 結果

| 確認項目 | 結果 | 確認した内容 |
|----------|------|-------------|
| `clasp push` とビルド結果の読み込み | 確認済み | 送った14ファイルが取り戻した内容と一致し、エディタから `setupProject` を実行できた（監査ログ「初期設定・成功」） |
| `setupProject` | 確認済み | 署名用の鍵、フォーム送信トリガー、督促トリガー（1時間ごと）が作られた |
| フォーム送信トリガーのイベント | 確認済み | 3件の申請が申請一覧に登録され、承認経路が決まり、承認依頼メールが送られた |
| 確認画面を開いただけでは状態が変わらないこと | 確認済み | 承認依頼メールのリンクを開いた時点では、申請一覧・承認トークンは変わらなかった |
| `Session.getActiveUser().getEmail()` | 確認済み（同じドメイン） | 同じ Workspace ドメインの承認者が開いたとき、メールアドレスが取得され、割り当てた承認者と照合できた |
| `google.script.run` | 確認済み（公開関数の呼び出し） | 確認画面から `submitDecision` を呼び、承認と却下を確定できた |
| 承認・却下と結果メール | 確認済み | 承認すると状態が「承認済み」になり、申請者に結果メールが届いた。却下は、コメントを入れて確定すると状態が「却下」になり、コメント入りの結果メールが届いた（コメントなしで確定できないことは試していない） |
| 1回限りのリンク | 確認済み | 使ったリンクをもう一度開くと「既に処理済み」と表示され、監査ログに TOKEN_USED が記録された |
| 督促（時間主導トリガー） | 確認済み | 最終通知から1時間を過ぎた申請に、督促1回目・2回目が送られた。督促回数・最終通知日時が更新され、トークンは古い行が「失効」、新しい行だけが「有効」になった |
| 督促で無効になったリンク | 確認済み | 督促1回目のリンクを2回目の後に開くと「このリンクは無効になっています」と表示され、監査ログに TOKEN_REVOKED が記録された |
| 時間主導トリガー実行時の操作者 | 確認済み | 督促がトリガーから実行され、TC-071 の操作者の検証で拒否されなかった |
| 組織外からウェブアプリを開いた場合 | 確認済み | 組織外のアカウントで承認のリンクを開くと、Google 側で開けなかった（ウェブアプリのアクセスを「組織内のユーザーのみ」にしているため） |
| フォームの「確認済み」メール収集 | 確認済み | 回答画面にログイン中のアドレスが表示され、回答者が別のアドレスを入力できなかった |
| メール送信 | 一部確認 | 承認依頼・結果（承認・却下）・督促が届き、リンクを開けた。管理者への通知は、送る条件（送信の失敗など）を起こしていないため未確認 |
| スコープ | 一部確認 | 4つのスコープのまま、上記の機能がすべて動いた。権限の同意画面に表示された一覧は記録していない |
| `Utilities` の HMAC・base64 | 一部確認 | GAS 上で発行した署名付きのリンクが、GAS 上の検証で受理された。代替部品（Node.js）と同じ値になることは確かめていない |

確認できなかった項目は次のとおり。

| 確認項目 | 確認できなかった理由・確認するときの観点 |
|----------|---------------------------------------|
| 2段階の承認 | 同じドメインのアカウントが1つしかなく、1段目と最終承認者が同じ人になるため。2段目が加わる金額で、1段目の承認後に2段目の承認者へ依頼が届くこと |
| 同じ組織の、承認者ではない社員が開いた場合 | 同上。割り当てた承認者と一致せず、操作できないこと |
| 組織外からフォームに回答できないこと | 申請者を組織外のアカウントにするため、確認用のフォームでは限定を外した。導入時に [06_導入・運用手順](06_導入・運用手順.md) の 2.3 の設定で確認する |
| `google.script.run` で `_` で終わる関数を呼べないこと | 呼び出しを試していない。公式の説明（4章）と TC-061 による |
| テンプレートのエスケープ | HTML の記号を含む申請を送っていない。印字スクリプトレットで値がエスケープされること |
| 排他制御 | 同時に操作していない。`LockService` で同時操作が直列になること |

### 3.3 確認の中で見つかった点

| 内容 | 影響 | 扱い |
|------|------|------|
| Apps Script の FormApp でフォームを作ると、メールアドレスの収集は「回答者からの入力」になり、「確認済み」には設定できなかった。「確認済み」はフォームの設定画面で変更した | 導入の手順への影響はない。[06_導入・運用手順](06_導入・運用手順.md) の 2.3 で、画面から「確認済み」に設定する手作業が必要であることの裏付けになる | 記録のみ |
| 承認トークンのシートの「使用日時」が、日付だけの表示になる。値には時刻まで入っている（発行日時・有効期限は日時の表示） | 判定と記録への影響はない。シートを目で見たときに時刻が分からない | 次の版で表示の形式を指定する候補 |
| メールの有効期限が `2026-11-19T07:37:37.922Z` のように、協定世界時の ISO 8601 の書式で表示される（`src/Notifier.ts` の `toISOString()`）。管理者への通知の日時（`src/Main.ts`）も同じ書き方 | 期限の判定への影響はない。承認者が日本時間と読み違えるおそれがある | 次の版で日本時間の表示にする候補 |
| 督促トリガーは、登録した時刻（14:13）と異なる分（15:37・16:37）に動いた | 影響はない。督促は「最終通知から督促開始時間を過ぎたか」で判定するため、送られる時刻はトリガーの動く時刻で決まる | 記録のみ |
