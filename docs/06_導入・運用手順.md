## 1. 前提

| 項目 | 内容 |
|------|------|
| Google | Google Workspace のアカウント（管理者になる人）。申請者・承認者は同じドメイン |
| 手元の環境 | Node.js 22.18 以上、npm、clasp（Google 公式の Apps Script 用コマンドラインツール） |
| 権限 | 管理者がスプレッドシートとスクリプトの所有者になる |

## 2. 導入手順

### 2.1 手元でビルドとテスト

```bash
npm ci
npm test            # ビルド（src → dist）と全テスト。98件すべて合格することを確認
npm run sample-data # 架空の設定・承認ルール等を sample-data/ に CSV で作る
```

### 2.2 スプレッドシートを用意する

1. 新しいスプレッドシートを作る。
2. `sample-data/` の CSV を、ファイル名と同じ名前のシートとして取り込む（`設定` `承認ルール` `申請一覧` `承認トークン` `監査ログ`）。
3. `設定` シートの「最終承認者メール」「管理者メール」、`承認ルール` シートの承認者を実際の社員のアドレスに直す。**管理者メールはスプレッドシートの所有者と同じアドレスにする**（初期設定の実行条件）。

### 2.3 フォームを用意する

1. Google フォームを作り、次の順で質問を置く：部署（選択）・申請区分（選択）・品目・内容（記述）・金額（記述・数値）・理由（段落）。
2. **【必須】メールアドレスの収集を「確認済み（Verified）」にする**（2列目に入る）。「回答者からの入力（Responder input）」は使わない。
   - 理由：手入力のアドレスは本人のものとは限らない。承認者 A が同僚 B のアドレスを入力して申請すると、本システムは申請者を B と判断するため、A の申請が A 自身に回り、自己承認の防止（申請者本人を承認者にしない処理）をすり抜けられる。
   - 本システムはスプレッドシートのフォーム送信トリガーで動き、受け取るのは回答シートの値だけである。フォーム側の設定が「確認済み」かどうかをスクリプトから確かめる方法は、公式の Apps Script リファレンス（Form クラス）で確認できなかった（`collectsEmail()` は収集の有無だけを返す）。そのため、この設定は導入手順での必須条件とし、2.8 の確認項目で実際に確認する。
3. **【必須】回答できる人を組織内（同じ Google Workspace）のユーザーに限定する**（フォームの設定画面の回答に関する項目。名称は導入時の画面で確認する）。
4. 社外のアドレスからの申請を確実に止めたい場合は、`設定` シートに「申請者ドメイン」（例：`example.com`）を追加する。指定したドメイン以外のアドレスの申請は受け付けず、管理者に知らせる。
5. 回答の保存先を 2.2 のスプレッドシートにし、シート名が `フォームの回答 1` になることを確認する。

### 2.4 スクリプトを配置する

1. スプレッドシートから Apps Script のエディタを開き、プロジェクトの設定画面でスクリプト ID を控える。
2. `.clasp.json.example` を `.clasp.json` に複製し、`YOUR_SCRIPT_ID` を控えた ID に置き換える（`.clasp.json` は Git に含めない）。
3. 次を実行する。

```bash
clasp login      # 管理者のアカウントで認証
npm run build    # dist/ を作る
clasp push       # dist/ の内容（*.js・*.html・appsscript.json）を送る
```

### 2.5 初期設定（鍵の生成とトリガーの登録）

1. エディタで関数 `setupProject` を選んで実行する。
2. 権限の確認画面で、次の4つに相当する権限だけが求められることを確認して許可する（画面の文言は要約であり、実際の表示とは異なる場合がある。理由は [04_権限設計](04_権限設計.md) の3章）。
   - このスプレッドシートの表示・編集
   - あなたとしてメールを送信
   - 外部（トリガー）でのスクリプトの実行
   - メールアドレスの参照
3. スクリプトのプロパティに `APPROVAL_HMAC_SECRET` が作られ、トリガーが2つ（フォーム送信・1時間ごと）登録されたことを確認する。
4. `監査ログ` に「初期設定・成功」の行が追加されたことを確認する。

### 2.6 ウェブアプリとして公開する

1. 新しいデプロイ（公開する版の登録）を作成し、種類をウェブアプリにする。
2. 実行するユーザーを「自分」、アクセスできるユーザーを「組織内のユーザー」にする（`appsscript.json` の `webapp` と同じ）。
3. 発行された URL（`https://script.google.com/` で始まり `/exec` で終わる）を、スクリプトのプロパティ `WEBAPP_URL` に保存する。
4. **デプロイ ID を控える。** コードを更新するときは同じデプロイを新しい版に更新する（新しいデプロイを作ると URL が変わり、送信済みのリンクが開けなくなる）。

### 2.7 シートを保護する

`申請一覧` `承認トークン` `監査ログ` `承認ルール` `設定` の各シートを保護し、編集できる人を管理者だけにする。申請者・承認者にはスプレッドシートを共有しない。

**注意：シートの保護は、スプレッドシートの編集者には効かない前提で考える。** 編集者はスクリプトのエディタを開いてスクリプトのプロパティ（署名用の鍵）を読めるほか、承認トークンや申請一覧を書き換えられるため、承認を自由に操作できる。スプレッドシートの編集権限は管理者（1〜2名）だけに付ける（[04_権限設計](04_権限設計.md) の6章）。

### 2.8 導入時の確認（Google 環境）

テスト用のアカウント（申請者1・承認者2）で次を確認する。結果は [05_テスト仕様書](05_テスト仕様書.md) の3章に追記する。

| 確認 | 期待する結果 |
|------|--------------|
| 3万円の申請を送る | 申請一覧に「承認待ち」で登録され、部署の承認者にメールが届く |
| 承認者がリンクを開く | 確認画面が表示される。この時点で申請一覧の状態は変わらない |
| 承認者以外のアカウントで同じリンクを開く | 「承認者として確認できませんでした」と表示される |
| 承認 →「確定する」 | 「承認済み」になり、申請者にメールが届く |
| 同じリンクをもう一度開く | 「既に処理済みです」と表示される |
| 15万円の申請を送り、1段目を承認 | 最終承認者に新しいリンクが届く |
| 却下（理由を入力） | 「却下」になり、申請者に理由付きのメールが届く |
| 24時間放置する（または設定の「督促開始時間」を1にして確認） | 督促メールが届き、古いリンクは「無効」になる |
| フォームを開く（組織外のアカウント・ログインなし） | 回答できない（組織内に限定した設定の確認） |
| フォームを開く（組織内のアカウント） | メールアドレスが自分のアカウントのもので表示され、別のアドレスを入力できない（「確認済み」の設定の確認） |
| `Session.getActiveUser()` の値 | 承認画面で承認者のメールアドレスが取得できる（取得できないと全員が「承認者として確認できませんでした」になる） |

## 3. 運用

| 作業 | 手順 |
|------|------|
| 承認ルールの変更 | `承認ルール` シートを編集する。上の行が優先される。保存後の新しい申請から反映される |
| 承認者の不在 | 一時的に `承認ルール` の承認者を代理の人に変える。処理中の申請は督促の上限に達した後に管理者へ知らせが届くので、管理者が承認者に連絡する |
| 鍵の交換（漏えいが疑われる場合） | 7.1 の手順で行う。送信済みのリンクはすべて無効になる。承認待ちの申請には督促で新しいリンクが送られるが、督促回数が督促上限回数に達している申請には送られない |
| コードの更新 | `npm test` → `npm run build` → `clasp push` → 既存のデプロイを新しい版に更新する |
| 監査ログの保管 | 年に1回、`監査ログ` を別のスプレッドシートに複製して保管し、元のシートの古い行を管理者が整理する（導入先の規程に合わせる） |
| 受付の失敗 | 管理者に「申請を受け付けられませんでした」のメールが届く。理由コード（[03_詳細設計](03_詳細設計.md) の例外表）を見て、申請者に再申請を依頼するか設定を直す |

## 4. 障害時の対応

詳しい対応は [07_障害対応手順書](07_障害対応手順書.md) を参照する。

承認・却下は「状態の保存」を先に行い、メールはその後に送る。メールが送れなくても状態は戻さない。

| 起きたこと | システムの動き | 管理者の対応 |
|------------|----------------|--------------|
| 申請受付後、承認依頼メールが送れない | 申請は「承認待ち」で登録済み。監査ログに「通知・失敗」、管理者にメール | 送信できない原因（メール送信数の上限への到達・宛先の誤り）を取り除く。督促（最後の通知から督促開始時間の経過後）で新しいリンクが自動で送られる。急ぐ場合は承認者に直接連絡する |
| 1段目の承認後、最終承認者へのメールが送れない | 承認は確定し、申請は「承認待ち（2段目）」。承認者には「次の承認者への通知に失敗したため、管理者に連絡しました」と表示 | 同上（督促で最終承認者に新しいリンクが送られる） |
| 最終承認・却下の後、申請者への結果メールが送れない | 状態は「承認済み」または「却下」で確定。管理者にメール | 督促の対象ではないため自動では送られない。`申請一覧` で結果を確認し、申請者に直接連絡する |
| 督促メールが1件送れない | その申請だけ「督促・失敗」を記録し、次の1時間ごとの見回りで再び試す | 失敗が続く場合は宛先（承認ルール）を確認する |
| 管理者へのメールも送れない | GAS の実行ログに記録する | 監査ログの「通知・失敗」「督促・失敗」を定期的に確認する |
| 処理は完了したが監査ログに記録できない | 管理者に「監査ログに記録できませんでした」のメール（日時・申請ID・操作・実行者・結果・詳細） | 下の 4.1 の手順で監査ログに追記する |
| 保存の確認（flush）に失敗 | 承認・却下は「保存できたか確認できませんでした」と表示し、管理者に「保存を確認できませんでした」のメール。受付は受付失敗のメール。督促は、その回の最後の確定に失敗すると管理者に「督促の保存を確認できませんでした」のメール | 下の 4.2 の手順で照合する |
| 督促の1回分の処理全体が行われない | 監査ログに申請IDの無い「督促・失敗」（詳細に BUSY・INVALID_SETTING 等）を記録し、次の1時間ごとの見回りで再び試す | 詳細のコードを [07_障害対応手順書](07_障害対応手順書.md) の 3.2 で振り分ける。INVALID_SETTING は管理者へのメールが届かないため、定期点検で監査ログを確認する |

### 4.1 監査ログの記録漏れを補う

1. メールの申請ID・操作・日時を控える。
2. `申請一覧` でその申請の状態を確認し、メールの内容（例：操作が「承認」なら状態が「承認済み」または次の段階）と一致することを確認する。
3. `監査ログ` の末尾に、メールの値を1行追記する。詳細の欄には「手動追記（記録漏れの補い）」と管理者名を書き添え、手で補った行と分かるようにする。
4. 記録漏れが続く場合は、シートの行数・容量・保護の設定を確認する。

### 4.2 保存の確認（flush）に失敗したときの照合

書き込みは「すべて反映」「一部だけ反映」「反映されていない」のいずれもありうる。

1. `申請一覧` で該当の申請（受付の場合はフォームの回答シートの最終行の申請）の状態を確認する。
2. `承認トークン` で該当の段階のトークンの状態を確認する。送られていないはずのトークン（「通知・失敗」「督促・失敗」の申請の、その日時に発行された行）が「有効」のまま残っていれば「失効」に変える。申請の状態が更新済みでトークンが「有効」のまま残っている場合は、「失効」に変える（残っていても再利用は拒否されるが、記録をそろえるため）。
3. 申請の状態が更新されていない場合は、承認者にもう一度リンクから操作するよう依頼する。更新されている場合は、承認者と申請者に結果を連絡する（結果の通知メールは送られていない）。
4. 受付で申請一覧に登録されていない場合は、申請者に再申請を依頼する。登録されている場合は督促で承認依頼が送られる。重複して登録されていないかも確認する。
5. 督促の場合、督促メール・管理者通知は各申請のトークンの行と督促回数・最終通知日時を確定してから送っているため、届いたリンクは使え、同じ督促が重複することもない。監査ログに「督促・成功」「管理者通知・成功」の行が欠けていれば 4.1 の形で補う。「督促・失敗」の申請で、`申請一覧` の最終通知日時がその回の日時のまま（送信失敗後の戻しが反映されていない）なら、督促開始時間が過ぎるまで再び督促されないため、承認者に直接連絡する。
6. 管理者に「申請の記録を戻せませんでした」のメールが届いた場合（監査ログの詳細 RESTORE_FAILED）は、メールの「戻す値」のとおり `申請一覧` のその申請の督促回数・最終通知日時を直す。直さないと、督促は督促開始時間が過ぎるまで再び送られず、督促上限の管理者通知は二度と再試行されない。
7. 管理者に「送れなかったリンクを失効できませんでした」のメールが届いた場合（監査ログの詳細 REVOKE_FAILED）は、`承認トークン` のその申請・段階で、発行日時がメールの日時の行が「有効」なら「失効」に変える（承認者には届いていないリンクのため、失効させても影響は無い）。
8. 確認した結果を、4.1 と同じ形で監査ログに追記する。

## 5. 定期点検

| 時期 | 見るもの | 確認すること |
|------|----------|--------------|
| 毎日（営業日） | 管理者あてのメール（件名の先頭が `【管理者確認】`） | 届いたものを [07_障害対応手順書](07_障害対応手順書.md) の 3.1 で振り分け、対応が済んでいるか |
| 毎日（営業日） | `監査ログ` の結果が「失敗」の行 | 前回の点検以降の行に、未対応のものが無いか（管理者へのメールが届かない失敗もあるため、メールとは別に見る） |
| 毎月 | `申請一覧` の承認待ちの申請 | 督促回数が督促上限回数以上のまま残っている申請が無いか（督促では新しいリンクが送られないため、個別に対応する） |
| 毎月 | `承認ルール` `設定` | 承認者・最終承認者・管理者のアドレスが現在の担当者のものか |
| 毎月 | スプレッドシートの共有 | 編集できる人が管理者だけか（2.7） |
| 毎月 | トリガー | `onFormSubmit`（フォーム送信）と `sendReminders`（1時間ごと）の2つがあるか |
| 毎月 | `監査ログ` `承認トークン` の行数 | 行数の増え方（3章の「監査ログの保管」の時期の判断に使う） |
| 変更時 | コード | `npm test` が全件合格してから `npm run build` → `clasp push` → 既存のデプロイを新しい版に更新する（3章「コードの更新」） |
| 変更時 | 承認ルール・設定・フォーム | 変更後にテスト用のアカウントで申請し、監査ログの「受付・成功」の行と、承認依頼のメールが届いたことを確認する |

点検の担当（役割）と記録の残し方は運用で決める項目とする。

## 6. バックアップと戻し方

本システムにバックアップの機能は無い。データはすべてスプレッドシートとスクリプトのプロパティにあり、コードは本リポジトリにある。

| 対象 | 取り方 | 保存先 |
|------|--------|--------|
| スプレッドシート（`フォームの回答 1` `申請一覧` `承認ルール` `設定` `承認トークン` `監査ログ`） | スプレッドシートを複製する | 管理者だけが開ける場所（具体的な場所・頻度・保管期間は運用で決める項目） |
| コード | 配置した版のタグ（`vX.Y.Z`）を控える | 本リポジトリ |
| デプロイ | デプロイ ID と URL を控える（2.6） | 管理者の手元の記録 |
| スクリプトのプロパティ | `WEBAPP_URL` の値を控える。署名用の鍵は控えない（失った場合は 7.1 の手順で作り直す） | 管理者の手元の記録 |

複製には申請者のメールアドレス・申請内容と、承認トークンの記録が含まれる。共有の範囲は元のスプレッドシートと同じく管理者だけにする。

### 6.1 戻し方

1. 戻す前に、現在のスプレッドシートを複製して残す（戻した後に照合するため）。
2. `申請一覧` と `承認トークン` は**同じ時点の複製から一緒に**戻す。片方だけ戻すと、申請の状態とトークンの記録が食い違う（リンクが「このリンクは無効です。」等になる。[07_障害対応手順書](07_障害対応手順書.md) の ERR-016・ERR-019・ERR-022）。
3. `監査ログ` は戻さない（追記だけの記録であり、戻すと複製の後の記録が失われる）。複製の後に追記された行は残す。
4. 戻した後、複製の時点より後に受け付けた申請・確定した承認は失われている。`監査ログ` と手順1で残した複製で対象の申請を特定し、申請者に再申請を、承認者に再操作を依頼する。
   - 申請IDは `申請一覧` を見て採番するため、戻した後の同じ日の申請に、失われた申請と同じ申請IDが付くことがある。監査ログで照合するときは日時もあわせて見る。
5. コードを戻す場合は、控えたタグの版で `npm ci` → `npm test` → `npm run build` → `clasp push` を行い、既存のデプロイを新しい版に更新する（新しいデプロイを作ると URL が変わる）。
6. テスト用のアカウントで申請し、監査ログの「受付・成功」の行と、承認依頼のメールが届いたことを確認する。

## 7. 資格情報・鍵の更新

| 対象 | 保管場所 | 更新するとき |
|------|----------|--------------|
| 署名用の鍵（プロパティ名は [03_詳細設計](03_詳細設計.md) の 2.1） | スクリプトのプロパティ（コード・シート・ログ・メールには置かない） | 漏えいが疑われるとき、スプレッドシートの編集者が外れたとき（[04_権限設計](04_権限設計.md) の6章） |
| ウェブアプリの URL `WEBAPP_URL` | スクリプトのプロパティ | 新しいデプロイを作ったとき（通常は既存のデプロイを更新するため変わらない） |
| clasp の認証情報 | 配置する人の端末（clasp が保存する認証ファイル。`.gitignore` で Git に含めない） | 配置する人が変わるとき、端末を替えるとき（`clasp login` をやり直す） |

外部サービスの API キー・トークンは使っていないため、ほかに更新するものは無い。

### 7.1 署名用の鍵の更新

`setupProject` は、鍵が無い場合だけ新しく作る（既にある鍵は上書きしない）。そのため、更新はプロパティを削除してから `setupProject` を実行する。

1. 申請・承認の少ない時間帯を選ぶ。削除してから手順3が終わるまでの間は、申請は受け付けられず（管理者に受付失敗のメール。理由コード SECRET_NOT_CONFIGURED）、承認リンクは「このリンクは無効です。」になる。
2. 管理者が、スクリプトのプロパティから署名用の鍵のプロパティを削除する。
3. 管理者が、エディタで `setupProject` を実行する（管理者メールのアカウントで。トリガーも作り直されるが、重複はしない）。
4. `監査ログ` に「初期設定・成功」の行が追加され、詳細に「署名用の鍵」が含まれることを確認する。
5. 手順1の間に受け付けられなかった申請があれば、申請者に再申請を依頼する（`監査ログ` の「受付・失敗」で特定する）。

更新した後の動き（コードどおり）：

- それまでに送った承認依頼・督促のリンクは、すべて署名が一致せず「このリンクは無効です。」になる（ERR-014）。開いたままの確認画面から「確定する」を押しても同じになる（確定時にもリンクを先に検証するため）。
- `承認トークン` の古い行は、状態の列が「有効」のまま残るが、署名が一致しないため使えない（ERR-014）。その申請の次の督促のときに「失効」になる。
- 承認待ちの申請には、最終通知日時から督促開始時間（設定。初期値24時間）が過ぎた後の見回りで、新しい鍵で署名したリンクが督促として送られ、督促回数が1増える。更新の直後に一斉に送られるわけではない。
- 督促回数が督促上限回数に達している申請は、督促の代わりに管理者へ知らせが届くだけで、新しいリンクは送られない。管理者へ知らせた後の申請（督促回数が上限＋1）も同じで、本システムには新しいリンクを送り直す機能は無い。これらの申請の扱い（承認者への連絡・申請し直しの依頼など）は運用で決める項目とする。

### 7.2 ウェブアプリの URL の更新

1. 新しいデプロイを作った場合だけ行う。発行された URL を `WEBAPP_URL` に保存する（`https://script.google.com/` で始まらない値は受け付けず、申請の受付が止まる）。
2. 送信済みのリンクは古い URL のままである。承認待ちの申請は、督促で新しい URL のリンクが送られる（7.1 の督促の条件と同じ）。
3. テスト用のアカウントで申請し、承認依頼のリンクが開けることを確認する。

## 8. 連絡体制

| 役割 | 担うこと | 連絡する先 |
|------|----------|------------|
| 利用者（申請者・承認者） | 申請・承認の操作。画面の文言とメールの件名を添えて、困ったことを連絡する | 運用担当者 |
| 運用担当者（管理者） | 定期点検（5章）、[07_障害対応手順書](07_障害対応手順書.md) に沿った切り分けと対処、利用者への連絡、障害の記録 | 保守担当者（コードの修正・配置が必要なとき、原因が分からないとき、不正な操作の疑いがあるとき） |
| 保守担当者 | コードの調査・修正、`npm test`、配置（`clasp push`・デプロイの更新） | 運用担当者（対処の結果を返す） |

連絡の手段・受付時間・各役割の担当者は運用で決める項目とする。本書には個人名・連絡先を書かない。
