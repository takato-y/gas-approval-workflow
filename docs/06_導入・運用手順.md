## 1. 前提

| 項目 | 内容 |
|------|------|
| Google | Google Workspace のアカウント（管理者になる人）。申請者・承認者は同じドメイン |
| 手元の環境 | Node.js 22.18 以上、npm、clasp（Google 公式の Apps Script 用コマンドラインツール） |
| 権限 | 管理者がスプレッドシートとスクリプトの所有者になる |

## 2. 導入手順

### 2.1 手元でビルドとテスト

```bash
npm ci
npm test            # ビルド（src → dist）と全テスト。68件すべて合格することを確認
npm run sample-data # 架空の設定・承認ルール等を sample-data/ に CSV で作る
```

### 2.2 スプレッドシートを用意する

1. 新しいスプレッドシートを作る。
2. `sample-data/` の CSV を、ファイル名と同じ名前のシートとして取り込む（`設定` `承認ルール` `申請一覧` `承認トークン` `監査ログ`）。
3. `設定` シートの「最終承認者メール」「管理者メール」、`承認ルール` シートの承認者を実際の社員のアドレスに直す。**管理者メールはスプレッドシートの所有者と同じアドレスにする**（初期設定の実行条件）。

### 2.3 フォームを用意する

1. Google フォームを作り、次の順で質問を置く：部署（選択）・申請区分（選択）・品目・内容（記述）・金額（記述・数値）・理由（段落）。
2. 回答者のメールアドレスを収集する設定にする（2列目に入る）。
3. 回答の保存先を 2.2 のスプレッドシートにし、シート名が `フォームの回答 1` になることを確認する。

### 2.4 スクリプトを配置する

1. スプレッドシートから Apps Script のエディタを開き、プロジェクトの設定画面でスクリプト ID を控える。
2. `.clasp.json.example` を `.clasp.json` に複製し、`YOUR_SCRIPT_ID` を控えた ID に置き換える（`.clasp.json` は Git に含めない）。
3. 次を実行する。

```bash
clasp login      # 管理者のアカウントで認証
npm run build    # dist/ を作る
clasp push       # dist/ の内容（*.js・*.html・appsscript.json）を送る
```

### 2.5 初期設定（鍵の生成とトリガーの登録）

1. エディタで関数 `setupProject` を選んで実行する。
2. 権限の確認画面で、次の4つに相当する権限だけが求められることを確認して許可する（画面の文言は要約であり、実際の表示とは異なる場合がある。理由は [04_権限設計](04_権限設計.md) の3章）。
   - このスプレッドシートの表示・編集
   - あなたとしてメールを送信
   - 外部（トリガー）でのスクリプトの実行
   - メールアドレスの参照
3. スクリプトのプロパティに `APPROVAL_HMAC_SECRET` が作られ、トリガーが2つ（フォーム送信・1時間ごと）登録されたことを確認する。
4. `監査ログ` に「初期設定・成功」の行が追加されたことを確認する。

### 2.6 ウェブアプリとして公開する

1. 新しいデプロイを作成し、種類をウェブアプリにする。
2. 実行するユーザーを「自分」、アクセスできるユーザーを「組織内のユーザー」にする（`appsscript.json` の `webapp` と同じ）。
3. 発行された URL（`https://script.google.com/` で始まり `/exec` で終わる）を、スクリプトのプロパティ `WEBAPP_URL` に保存する。
4. **デプロイ ID を控える。** コードを更新するときは同じデプロイを新しい版に更新する（新しいデプロイを作ると URL が変わり、送信済みのリンクが開けなくなる）。

### 2.7 シートを保護する

`申請一覧` `承認トークン` `監査ログ` `承認ルール` `設定` の各シートを保護し、編集できる人を管理者だけにする。申請者・承認者にはスプレッドシートを共有しない。

### 2.8 導入時の確認（Google 環境）

テスト用のアカウント（申請者1・承認者2）で次を確認する。結果は [05_テスト仕様書](05_テスト仕様書.md) の3章に追記する。

| 確認 | 期待する結果 |
|------|--------------|
| 3万円の申請を送る | 申請一覧に「承認待ち」で登録され、部署の承認者にメールが届く |
| 承認者がリンクを開く | 確認画面が表示される。この時点で申請一覧の状態は変わらない |
| 承認者以外のアカウントで同じリンクを開く | 「承認者として確認できませんでした」と表示される |
| 承認 →「確定する」 | 「承認済み」になり、申請者にメールが届く |
| 同じリンクをもう一度開く | 「既に処理済みです」と表示される |
| 15万円の申請を送り、1段目を承認 | 最終承認者に新しいリンクが届く |
| 却下（理由を入力） | 「却下」になり、申請者に理由付きのメールが届く |
| 24時間放置する（または設定の「督促開始時間」を1にして確認） | 督促メールが届き、古いリンクは「無効」になる |

## 3. 運用

| 作業 | 手順 |
|------|------|
| 承認ルールの変更 | `承認ルール` シートを編集する。上の行が優先される。保存後の新しい申請から反映される |
| 承認者の不在 | 一時的に `承認ルール` の承認者を代理の人に変える。処理中の申請は督促の上限超過で管理者に知らせが届くので、管理者が承認者に連絡する |
| 鍵の交換（漏えいが疑われる場合） | スクリプトのプロパティ `APPROVAL_HMAC_SECRET` を削除して `setupProject` を再実行する。送信済みのリンクはすべて無効になるため、承認待ちの申請は次の督促で新しいリンクが送られる |
| コードの更新 | `npm test` → `npm run build` → `clasp push` → 既存のデプロイを新しい版に更新する |
| 監査ログの保管 | 年に1回、`監査ログ` を別のスプレッドシートに複製して保管し、元のシートの古い行を管理者が整理する（導入先の規程に合わせる） |
| 受付の失敗 | 管理者に「申請を受け付けられませんでした」のメールが届く。理由コード（[03_詳細設計](03_詳細設計.md) の例外表）を見て、申請者に再申請を依頼するか設定を直す |
