## 状況

承認者にはメールでリンクを送る。リンクを推測・改ざん・転送・再利用されると、なりすましや二重承認が起きる。また、メールのセキュリティ製品はリンクを自動で先読みすることがあり、「開いただけで承認」になる作りは誤承認を招く。

## 検討した案

| 案 | 内容 | 判断 |
|----|------|------|
| A | 申請IDだけをリンクに入れる | 推測・改ざんが容易。不採用 |
| B | 乱数のトークンだけをシートに保存して照合 | 推測は難しいが、有効期限・段階の改ざん検知をシートの記録だけに頼る |
| C | HMAC 署名付きのトークン（中身に期限・段階）＋シートで1回限りを管理＋承認者本人の確認＋確認画面 | 採用 |

## 決定

- トークンは `base64url(中身)` + `.` + `HMAC-SHA256` の署名とし、鍵はスクリプトのプロパティに置く。
- 1回限りの判定と承認者の割り当てはサーバー側（承認トークンシート）に持つ。
- リンクを開く操作（GET）では状態を変えず、確認画面で「承認する／却下する」→「確定する」の2回の操作をしたときだけ確定する。
- 確定の操作には、確認画面を表示するたびに作る署名付きの確認用の値（本人・15分の期限）を必須にする。
- 状態の判定は排他制御の中で読み直して行い、承認済み・却下からの操作は拒否する。

## 理由

- 署名で中身の改ざんを、記録で再利用を、本人確認で転送されたリンクの悪用を、確認画面で先読みと押し間違いを防げる。それぞれが別の攻撃に対応し、どれか1つが破られても他で止まる。

## 影響

- 鍵の管理が必要になる。漏えい時は鍵を作り直し、出回っているリンクをすべて無効にする（督促で再発行される）。
- 制約：鍵を作り直した後、督促回数が督促上限回数に達した申請（管理者への知らせの前後とも）には、督促で新しいリンクが送られない。リンクを送り直す機能は持たないため、該当する申請は運用で扱う（[04_権限設計](../04_権限設計.md) の 7.1、[06_導入・運用手順](../06_導入・運用手順.md) の 7.1）。
- 承認者がリンクを開くには、同じドメインの Google アカウントでのログインが必要になる。
